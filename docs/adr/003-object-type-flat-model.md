# ADR-003: 对象类型从树层级模型调整为平表属性模型

## 状态

已接受

## 上下文

项目当前存在根本性的数据模型错误：

1. **树层级误解**：开发者把 Excel 中"一级"列的值（经营/发展/交付/服务）当成了树的第一层父节点，"二级"列当成了子节点，再把真正的指标（营业收入/5G用户数）作为叶子节点。

2. **Excel 实际结构**：每个指标是一行平表数据，有 39 个属性列。一级、二级、颗粒度、关注频率、指标值单位、对接部门等是**平行的属性字段**，彼此之间没有父子层级关系。

3. **0602 会议结论**：
   - "屏"等具体类型应作为**独立的对象类型**
   - 对象类型模块需**直接建立实例层级**
   - 指标名称**降级为属性**
   - 属性管理**失去独立维护意义**，需合并到对象类型管理中

由此产生核心架构问题：在代码中如何表达"对象类型 = 属性字段定义，指标 = 对象类型实例的组合实体"这一关系？

## 决策

采用**混合模型**：

- **代码层**：`Indicator` 接口采用**平表模型**，直接包含所有字段（一级、二级、颗粒度、指标编码、指标值单位等），与 Excel 结构一致。
- **UI 层**：指标详情/编辑页面按**对象类型分组展示**字段（如【指标标识】组、【分类属性】组、【指标值单位】组等），每个组可折叠展开。
- **对象类型枚举值管理**：作为配置面板嵌入对象类型管理中，维护每个对象类型的可选值（如"一级"有哪些值：经营/发展/交付...）和数据源映射规则。

## 备选方案

| 方案 | 描述 | rejected 原因 |
|------|------|--------------|
| A — 严格分层模型 | 代码中严格区分 `ObjectType` → `ObjectTypeInstance` → `Indicator`（组合引用） | 实现过于复杂，对 demo 级别过度设计。Excel 数据是平表，严格分层会引入不必要的抽象层和转换成本。 |
| B — 纯平表模型 | 代码平表，UI 也不分组，所有字段平铺展示 | 无法体现"对象类型"的概念，与 0602 会议结论（对象类型需建立实例层级）冲突。UI 上 39 个字段平铺过于冗长。 |
| C — 混合模型（代码平表 + UI 分组） | **已选**。代码用平表与 Excel 一致，UI 按对象类型分组展示，兼顾实现简单和概念清晰。 | — |

## 理由

1. **与 Excel 数据结构一致**：平表模型直接映射 Excel 的 39 列数据，无需额外的转换层，导入逻辑简单直接。

2. **实现简单，demo 可快速交付**：混合模型在代码上是最轻量的，不需要引入复杂的元数据抽象层。对于当前纯前端 demo 的性质，平表足够表达语义。

3. **UI 分组满足"展示清楚"的目标**：0602 会议记录明确提到"当前重点不是出报表，而是先完成关系维护和属性配置"。UI 按对象类型分组（可折叠）既体现了对象类型的概念，又避免了 39 个字段平铺的混乱。

4. **为未来严格分层预留演进空间**：如果未来需要迁移到严格的 `ObjectType` + `ObjectTypeInstance` 模型，平表接口可以逐步重构为组合引用，当前的设计不会成为阻碍。

5. **属性管理合并的自然落地**：对象类型的枚举值管理（如"一级"有哪些值）作为配置面板嵌入，不单独成页，与 0602 会议"属性管理失去独立维护意义"的结论一致。

## 后果

- **正面**：
  - 与 Excel 数据源结构一致，导入逻辑简单
  - 实现成本低，适合 demo 快速交付
  - UI 分组展示兼顾了概念清晰和用户体验
  - 为未来架构演进预留了空间

- **负面**：
  - 对象类型的定义（枚举值、数据源映射规则）在代码中不够显式，主要通过 UI 配置面板表达
  - 如果未来需要支持多对象类型（不仅是"指标"，还有"产品"、"客户"等），平表模型需要重构为严格分层
  - `Indicator` 接口包含 39+ 个字段，较为臃肿（可通过按对象类型分组的子接口缓解）

## 相关术语修正

本次决策联动修正了以下术语定义（见 `CONTEXT.md`）：

| 术语 | 旧定义 | 新定义 |
|------|--------|--------|
| 对象类型 | 指标的分类维度，如经营/发展/交付/服务 | 指标的属性字段定义，如一级、二级、颗粒度、指标标识等 |
| 指标 | 业务数据指标，是图谱中的核心节点 | 多个对象类型实例的组合实体，代码中表现为平表实体 |
